# Spec 2 — Base Cortex (confirm & adapt, not rebuild)

Status: design only. Cortex already exists and is tested
(`python -m tests.test_cortex`); this spec documents what it is, confirms it
needs **zero structural changes** for the Qwen/harness pivot, and names the
one thing that does change (who calls it, not what it does).

## 1. Why Cortex doesn't need a rewrite

`cortex/writeback.py` already states the design intent: "Cortex itself stays
model-agnostic... inference-time scaffolding only." Every function in
`cortex/` operates on plain data (`Episode`, embeddings, graph weights) — no
`anthropic` or any provider import anywhere in the package. Switching the
pipeline's LLM provider from Claude to Qwen changes *what produces* an
`Episode`'s `abstracted_pattern`/`failure_summary` fields; it changes nothing
inside `cortex/` itself.

## 2. Components (as built, for reference)

- **Schema** (`cortex/schema.py`): `Episode` (problem_summary, action_arc,
  healer_attempts, outcome, abstracted_pattern, failure_summary,
  distilled_learnings, cost_actual, domain, scope), plus
  `salience_boost()` — the predicted-vs-actual difficulty surprise signal.
- **Store** (`cortex/store.py`): ChromaDB-backed `recall` / `intuition` /
  `caution` / `instinct` collections (vector search per index), plus
  `episodes.jsonl` as the Tier-2 full structured-arc log.
- **Graph** (`cortex/graph.py`): NetworkX `MultiDiGraph`, "groove" edge
  weights, Hebbian `reinforce()` (success strengthens, failure weakens),
  topic-scoped exponential `decay_all()`, `spreading_activation()` for
  associative (non-literal-similarity) retrieval. Persisted to SQLite
  (`graph.sqlite3` — nodes/edges tables, transactional per-mutation commits),
  not a single JSON blob — a crash mid-write loses at most the one
  in-flight change, not the whole graph.
- **Retrieval** (`cortex/retrieval.py`): queries all four indices + expands
  via spreading activation, renders a single `to_prompt_text()` block
  (Recall / Intuition / Caution / Instinct sections) for injection into a
  prompt.
- **Replay** (`cortex/replay.py`): greedy cosine-similarity clustering over
  Intuition entries, a model-backed `compare_fn` decides same-pattern or
  not, confirmed clusters (≥3 independent episodes) promote to Instinct,
  rejected clusters down-weight their spurious edges, then a decay+prune pass.
- **Write-back** (`cortex/writeback.py`): persists the episode, adds/updates
  graph nodes, reinforces/weakens `co_retrieved_with` edges for whatever was
  surfaced this round, flags `contradicts` edges when a heeded Intuition hit
  still led to failure.

## 3. The one real integration point: who supplies the model calls

Two places in the existing design take a model-backed callable/output rather
than doing their own inference:

1. **`run_replay(..., compare_fn)`** — `compare_fn: Callable[[list[str]],
   tuple[bool, str|None]]`, decides if a cluster of abstracted patterns is
   really the same underlying pattern. Today nothing calls this with a real
   model yet in the research pipeline; phase 4+ needs a thin Qwen-backed
   `compare_fn` (reuses `harness/providers/qwen.py`, not a new provider path).
2. **Episode's `abstracted_pattern` / `failure_summary` / `distilled_learnings`**
   — generated by a Reflection stage (Spec 1 §6) before `write_back()` is
   called. This replaces today's Claude-specific `LearningAgent` with a
   Qwen-backed equivalent; same three-field output contract, same place in
   the flow (after Grader/Reviser settles, before write-back).

Neither requires touching a single line inside `cortex/`.

## 4. The boundary this project needs to keep explicit: Scratchpad vs. Cortex

This is the part worth spelling out precisely, since both are "memory" but
answer different questions:

| | Scratchpad (`harness/notebook.py`) | Cortex (`cortex/`) |
|---|---|---|
| Scope | One episode | Across all episodes, forever |
| Lifetime | Written during the episode, saved to `workspace/<id>/notebook.json` for crash-recovery, not read again after the episode ends | Written once at episode end, read at the *start* of every future episode |
| Question it answers | "What have I found out so far, in this task?" | "What have I learned, in general, from past tasks like this?" |
| Mechanism | Plain append + render to markdown | Vector search (Recall/Intuition/Caution/Instinct) + groove graph + spreading activation + sleep-replay consolidation |
| Who writes it | Harness code, deterministically, after each stage | The Reflection stage's model output, via `write_back()` |

Concretely: the Investigator's distilled findings go into the **Notebook**
so the Synthesizer can read them *within this episode*. The Reflection
stage's `abstracted_pattern` (e.g. "cross-check numeric claims against 2+
sources before citing") goes into **Cortex** so the *next* episode's Planner
can see it as Intuition/Instinct before research even starts.

## 5. Domain scoping (already supported, just needs to be used consistently)

`Episode.domain` already exists for exactly this purpose — `"coding"` vs.
`"research"` (and later `"fintrack"`, `"fittrack"`, ...) keep each project's
memory and groove graph topics separate within the same Cortex store, while
still allowing cross-domain `scope` filtering if ever wanted. No schema
change needed; just make sure every harness sets `domain` correctly on write
and `tracer.build_report(..., domain=...)` filters correctly on read (already
implemented in `selfmod/tracer.py`).

## 5a. Relationship to Harness²'s "harnessing-level recursion" (Spec 5)

Harness²'s design names a "persistent improvement harness" that accumulates
adopted edits and "evidence-supported lessons" across tasks. **That's Cortex
— not a second memory store to build.** When Spec 5 talks about
harnessing-level recursion persisting lessons across research episodes, it
means: Reflection's output already goes into Cortex via `write_back()`
(§3), and `selfmod`/RSI's own `tracer.build_report()` already reads Cortex
back out to inform the next Proposer step (Spec 5 §3). No new persistence
layer — Harness²'s vocabulary just describes a capability this project
already has under a different name.

## 6. Open questions

1. Nothing structural — the only decision is *when* to wire a real
   `compare_fn` into Replay for the research domain (needed for Instinct
   promotion to actually happen; not needed for phase 4's basic
   retrieve→write-back loop to work).
2. Should Replay be scheduled (cron, alongside the self-improvement cycle)
   once the research harness has enough episodes, or stay purely on-demand
   as it is today? Not blocking phase 4.
